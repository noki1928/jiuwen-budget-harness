# Budget-aware харнесс на openJiuwen

Харнесс решает пакет задач (coding / math / data_analysis / search / прочие) за минимум токенов.
Главная идея: **модель не получает shell там, где он не нужен**. Обёртка сама запускает тесты,
собирает минимальный промпт, разбирает ответ, применяет его, перепроверяет и пишет `answer.txt`.
LLM вызывается через `openjiuwen.core.foundation.llm.Model`.

## Сборка и запуск

```bash
docker build -t hack:latest .
docker run --rm -e LLM_BASE_URL -e LLM_API_KEY \
  -v "$TASKS:/data/tasks:rw" --read-only --tmpfs /tmp:rw,size=2g -e HOME=/tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --workdir /app --entrypoint python hack:latest /app/run_agent.py --tasks-dir /data/tasks
```

| Переменная | Назначение |
|---|---|
| `LLM_BASE_URL`, `LLM_API_KEY` | прокси организаторов (ключей в репозитории нет) |
| `OUT` или `--out` | файл решений (каталог → `solutions.json` внутри). По умолчанию `<tasks-dir>/solutions.json` |
| `TOKEN_BUDGET` | необязательно: известный бюджет в выходных токенах, планировщик не начнёт задачу, на которую не хватит |
| `LLM_CONCURRENCY` | параллельных запросов к прокси, по умолчанию 5 |
| `TIME_LIMIT_S` | после этого времени новые задачи не начинаются, по умолчанию 52 мин (контейнер живёт 60) |
| `TRAJ_DIR` | куда писать траектории, по умолчанию `/tmp/trajectories` |

Результат каждой задачи: `answer.txt` в каталоге задачи **и** в её `workspace/` (инструкции просят
«текущий каталог», регламент — «каталог задачи»; пишем в оба). Файл решений перезаписывается
атомарно (`tmp` + `rename`) после каждой решённой задачи.

Образ: `python:3.12.8-slim-bookworm` + `openjiuwen==0.1.19`, все зависимости закреплены в
`requirements.lock` (снят `pip freeze` из собранного образа). Размер ≈1.4 ГБ, сборка ≈80 с.
Корень контейнера read-only: `PYTHONDONTWRITEBYTECODE=1`, логи openJiuwen перенаправлены в `/tmp`.

## Архитектура

Отдельного LLM-оркестратора нет: планирование детерминированное и бесплатное.

```
run_agent.py
 1. recon (без LLM, параллельно): тип задачи по форме workspace, прогон тестов,
    число падений, признаки невыполнимости
 2. plan: оценка стоимости → сортировка по reward / est, подозрительные — в конец,
    гарантированно невыполнимые — пропуск
 3. solve: очередь + 5 воркеров, общий учёт бюджета, дедлайн по времени
jw_harness/
  llm.py      openJiuwen Model, учёт расхода (input/10 + output), семафор, ретраи 429/5xx
  solvers.py  coding / math / data / search / agent
  mathfix.py  безопасный разбор и вычисление кода из ответа модели
  dataq.py    безопасное исполнение SQL (SQLite в памяти) и pandas-выражений над CSV
  kbgraph.py  база знаний из markdown → граф сущностей; подграф и путь-запросы
```

### Решатели

**coding** («почини `mylib.py`, пока тесты не пройдут»). Обёртка гоняет тесты, вытаскивает только
упавшие `assert` с фактическим значением и номерованный код виноватых функций (через AST).
Модель отвечает строками `N: код`; отступ берётся из исходной строки (модели плохо считают
пробелы), правка, ломающая синтаксис, откатывается. До 3 раундов на `qwen3.6-35b-a3b-noreason`
(каждый раунд — новый короткий контекст только с оставшимися падениями), затем один раунд
`qwen3.8-27b-noreason` с переписыванием функции целиком. Потолок — 4× оценки.

**math** (текстовые задачи). Модель переводит каждое предложение в строку Python, обновляя `x`
(`x -= x*20//100`), а **считает Python**: модели надёжно переводят и плохо вычисляют
(ответ числом сразу — 1/22, кодом — 82/82). `mathfix.py` чинит ответ: баланс скобок,
`×÷−^`, `answer = …`, хвост `= 123`, `print(...)`, `import math`, fences, `if/else`; исполняется
только белый список AST (никаких импортов/атрибутов кроме `math.*`, ограничение на `**`).
Если код не вычислился — повтор на второй модели.

**data** (data_analysis с CSV). Модель видит заголовок и 3 строки каждой таблицы и вопрос и пишет
**один SQL-запрос**; `dataq.py` исполняет его в SQLite в памяти (authorizer пропускает только
SELECT/чтение/функции, один оператор, таймаут). `SUM` по пустой выборке (`NULL`) → `0`.
При ошибке исполнения — один повтор с текстом ошибки, затем pandas-выражение на второй модели
(белый список AST: только имена таблиц и `df`, без `_*`, `to_*`, `read_*`, `eval`, `query`...),
затем агентный цикл.

**search** (база знаний из markdown). `kbgraph.py` без LLM разбирает файлы в граф: заголовок
`# Имя` — сущность, строки `Ключ: Значение` (и `- **Ключ:** Значение`) — поля, значение,
совпадающее с заголовком другого файла, — ссылка. Модель получает только **подграф**: сущности
из вопроса и всё, что достижимо за 2 шага (3–5 строк фактов), и отвечает значением.
Если она ответила `IMPOSSIBLE` — второе мнение: вторая модель пишет **путь-запрос**
`Имя > Поле > Поле` по схеме полей, обёртка проходит его по графу. Если база не разбирается в
граф — агентный цикл.

**agent** (всё остальное и фолбэк). Цикл JSON-действий `{"cmd"}` / `{"answer"}` с жёсткими
лимитами: в первом сообщении сразу список файлов и первые строки текстовых файлов, в контексте
только последние 3 обмена, вывод команд обрезан до 1500 символов, `max_tokens=350`, ≤8 шагов,
потолок 2500 единиц. Модель может ответить `IMPOSSIBLE` — тогда ответ не пишется.

### Оценка расхода

Стоимости измерены на тренировочных прогонах (`bench/`), единица = выходной токен,
вход /10, рассуждения считаются выходом (на прокси они входят в `completion_tokens`):

| вид | оценка | факт (медиана) |
|---|---|---|
| math | 70 | 65 |
| coding | 20 + 35 × число падающих тестов (известно до вызова LLM) | 45 |
| data (CSV) | 40 | 33 |
| search (граф) | 25 | 21 |
| data_analysis / search через агента | 250 / 300 | 110–210 / 180–290 |
| прочее | 1500 | — |

Приоритет = `reward / est`. При известном `TOKEN_BUDGET` задача не начинается, если на неё не
хватает половины оценки. Если прокси перестаёт отвечать (бюджет исчерпан на его стороне),
воркеры останавливаются; всё уже решённое сохранено.

### Невыполнимые задачи

Ищутся до траты токенов:
* coding: тесты, где одно и то же выражение сравнивается с разными константами → пропуск (0 токенов);
* search по графу: в вопросе есть имя, которого нет в базе, и нет ни одной известной сущности → пропуск (0 токенов);
* search без графа: имя «Имя Фамилия» из вопроса не встречается ни в одном файле → подозрительная;
* data_analysis: значение в кавычках из вопроса не встречается в данных → подозрительная;
* нет workspace у задачи, которой он нужен → подозрительная.

Подозрительные идут в конец очереди и получают ≤3 шага и ≤300 единиц. Неверный ответ не
штрафуется, поэтому «дешёвая попытка» выгоднее, чем полный отказ.

## Почему так: замеры (`bench/`)

Все цифры — `qwen3.6-35b-a3b-noreason`, если не указано иное.

* **Режимы.** Агентный цикл с bash: 140–690 единиц/задачу. Однократный вызов через обёртку:
  coding 45, math 68 — в 3–15 раз дешевле при той же или лучшей точности.
* **Модели** (coding 22 + math 22 задачи): `-noreason` варианты решают всё за ~55 ед.;
  рассуждения стоят в 3–25 раз дороже и не точнее (35b с рассуждениями — хуже всех).
  35b-noreason и 27b-noreason равны по качеству; их ошибки на 82 math-задачах не
  пересекались, поэтому 27b — второй шанс.
* **Промпт math** (82 задачи): полный английский с примером — 82/82 за 68; сжатые версии теряют
  6–25 задач, экономя ~7 ед. (вход стоит в 10 раз дешевле выхода, а без примера модель пишет
  длиннее). Китайский перевод: −12% входных токенов, 81/82, общая стоимость та же. Русский хуже.
* **Промпт coding:** короткий (24 токена) — 22/22 за 45 против 51 у длинного.
* **Температура:** 0 — лучшая (82/82); 0.7 — 79/82. Повтор делаем другой моделью, а не температурой.
* **data_analysis** (62 задачи, 3 схемы таблиц, 10 видов вопросов): SQL 61/62 за 33 ед.,
  pandas 60–62/62 за 37, агентный цикл 61/62 за 214. Ошибки двух моделей не пересекались.
* **search** (62 задачи, 1–3 шага, 7 невыполнимых): подграф 62/62 за 20 ед. на обеих моделях,
  путь-запрос 62/62 за 21, вся база в промпте 49/62 за 89, агентный цикл 48/55 выполнимых за 294
  (и ~289 на каждую невыполнимую). В харнессе: 55/55 за 21.7, невыполнимые отсеяны бесплатно.

Количество токенов промптов измерялось через сам прокси (`bench/tokcount.py`: `prompt_tokens` при
`max_tokens=1`), то есть ровно тем токенизатором и шаблоном чата, по которым идёт учёт.

## Траектории

Траектория каждой задачи (промпты, ответы, стоимость каждого вызова) пишется в `TRAJ_DIR`.
Тренировочные траектории лежат в `bench/runs/`:

* `bench/gen_train.py` — 20 coding (15 функций × 2 вида багов, 1–3 бага) + 20 math;
* `bench/gen_math.py` — 60 разнообразных math (6 сюжетов, 11 операций, 3 типа вопроса);
* `bench/make_infeasible.py` — невыполнимые варианты примеров;
* `bench/oneshot.py` — сравнение моделей/режимов/промптов, `bench/score.py` — проверка ответов.

Последний прогон в контейнере (с флагами организаторов): 38 выполнимых задач — 38/38,
≈3200 единиц, 40 с.
